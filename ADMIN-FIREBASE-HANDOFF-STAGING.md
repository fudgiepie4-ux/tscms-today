## Review of Cherish's October 19 #junk-drawer handoff — BLOCKERS CONFIRMED
Source: https://fudgiepieaigang.slack.com/archives/C0C924D7589/p1792452587502709

**Status: NOT ready for any production Admin login deployment.** These points follow directly from the exact rules reported by Cherish; deployed-rule state has not been independently read from Firebase Console.

1. **Pending registrations cannot be stored.** Current `match /users/{uid} {allow write: if false;}` rejects every client-side create and update. Firebase Auth account creation may succeed, but the user's registration profile will not be saved. Design tightly scoped authenticated `create` that enforces `uid == request.auth.uid`, only permitted fields, pending status, `admin == false`, `owner == false` (or role fields absent), authenticated email match, and immutable privilege fields; alternatively use a trusted server-side registration endpoint. No general client-side writes to role documents.
2. **Owner approval dashboard cannot list requests.** `allow list: if false` blocks all queries for `/users`. Design Owner-only list/approve/reject with exact authorization, or a dedicated requests collection with strict immutable/privilege-free signup writes and owner-only approval. Console-only approval is a valid temporary manual fallback but **not** the promised in-website owner dashboard.
3. **Owner is not provisioned.** Need authenticated Owner identity with email verified, plus a trusted out-of-band initial `/users/{uid}` record granting `owner:true, admin:true, status:approved`. Confirm login and deny owner privilege changes by other users. Client-only controls are insufficient.
4. **Email verification is not enforced.** Build verification email flow and server-rule protection requiring verified email for Admin reads (e.g. checking `request.auth.token.email_verified == true` where appropriate), then test both unverified/verified token states. UI checks alone are insufficient.
5. **Legacy encrypted bundle cannot be protected by merely changing the gate.** Public GitHub Pages continues to serve `admin-data.enc.json`. Anyone possessing the old password can download and decrypt it without Firebase role authorization, now or after November 1, even if the new website UI refuses them. Plan to migrate sensitive records to Firestore with enforced rules or an authenticated storage backend, then remove/rotate legacy public bundle and retire old decrypt route. Files already downloaded cannot be revoked. All current content must be accounted for before removal.
6. **Nov 1 PIN cutoff must be implemented without trusting the browser date or only hiding a button.** Owner-approved Firebase identities, not the PIN, should be the sole route to protected data. If there is any privileged registration path predicated on the PIN, its eligibility and cutoff must be enforced server-side; old PIN cannot be relied upon once shared. A PIN-only screen may be used as an informational transition funnel but must not grant a permission.
7. **Username login is unimplemented.** Native Firebase email/password supports email identity, not username-to-email lookup. Do not expose private email in publicly readable username mappings. A trusted backend (or an owner-approved email sign-in compromise with username as private profile/public nickname) is required. Agree on cost and UX before implementing this functionality.
8. **Cost caution:** Firebase Cloud Functions requires Blaze/pay-as-you-go (source https://firebase.google.com/docs/functions/quotas); project reportedly Spark/free. Do not enable billing without owner approval. Firestore rule-only owner authorization can support a carefully designed free-tier workflow if verified.
9. **No tests have been run.** Execute Cherish's 10 rule tests PLUS: signup create only pending (allowed), privilege injection rejected, email mismatch rejected, self-update to approved/owner denied, owner list/approve allowed, non-owner list/approve denied, unverified approved user denied, old PIN after cutoff yields no protected data, and Firefox/Brave phone end-to-end sign-in and logout. The Emulator Suite can run automated tests (https://firebase.google.com/docs/rules/unit-tests), but production deployment requires careful scoped verification too.

Priority: (A) bootstrap Owner privately and test safe read/deny, (B) design safe signup writes and Owner-only approval, (C) migrate protected Admin data out of publicly fetchable bundle, (D) complete email verification and username-login strategy, (E) regression/security testing and explicit owner approval, (F) switch over before Nov 1. No production merges based solely on a visual preview.

## October 19 — FULL v2 Firestore rules audit (exact Slack pasted rules, proposed/not deployed)
Source: https://fudgiepieaigang.slack.com/archives/C0C924D7589/p1792455385633259

**REVIEW RESULT: DO NOT APPROVE DEPLOYMENT OF v2 AS WRITTEN.** Current deployed v1 rules stay as-is until a tested revision and express owner approval. Confirmed Owner Firestore doc exists (user-provided screenshots); Owner browser sign-in and verified-email status are *not* yet verified.

### Concrete gaps in the actual posted expressions
1. **isAdmin/isOwner insufficient state checks**: `isAdmin()` tests only `email_verified`, existence and `admin==true`; it fails to check `status=='approved'`. `isOwner()` similarly checks only `owner==true`, ignoring status. Marking a user `status:'revoked'` or `status:'rejected'` but forgetting to clear the boolean would NOT revoke access. Require approved status and corresponding true boolean, with consistent transitions. Evaluate Owner policy carefully to prevent accidental self-lockout.
2. **PII exposure via allow get**: `allow get: if isOwner() || isAdmin() || self` permits any approved Admin who knows another UID to fetch that person's private `fullName` and `email`. Fudgie said emails must not appear as **public Gamehouse identity**, and account review belongs to Owner; default to Owner-only other-user profile reads plus self-get, with any staff-view subset separately scoped.
3. **Signup validation incomplete**: `keys().hasOnly(...)` does not require presence of `username`, `fullName`, `createdAt`; it does not validate types, nonblank lengths, allowed characters, `createdAt==request.time`, or allowed `registrationPath` beyond direct/pin. Use `hasAll` and type/length constraints, plus normalize email and username safely; verify `email` matches auth token. Reject invalid/malformed records. Note that Auth account creation itself occurs before profile storage; handle orphaned signup after denied profile write.
4. **Username uniqueness is NOT guaranteed**: `/users` creation never requires atomic ownership/reservation in `/usernames`, and `/usernames/{username}` client create allows an authenticated user to reserve arbitrarily many names with a fabricated or unrelated profile, without a profile link check. Case variants can bypass naive uniqueness. Require a single normalized identifier, atomic batch/transaction with `getAfter()` validation for both linked records, and Owner-controlled change/recovery. Do not expose private emails in public mappings. Firebase documents `getAfter()` for atomic validation: https://firebase.google.com/docs/firestore/manage-data/transactions
5. **Owner update overbroad**: `allow update: if isOwner() ...` allows Owner to change `status`, `admin`, `username`, `fullName`, timestamps and approval fields across other docs with few value/transition checks. Owner can accidentally set their own admin:false or status:revoked while retaining owner:true. Define per-action accepted changes and explicit Owner record protection (e.g. no client changes to owner==true record), plus coherent admin/status transitions and verified-email policy.
6. **PIN cutoff is manual, not automatic**: `/config/migration` field `cutoffDate` isn't referenced in rule logic. `pinRegistrationOpen` must be manually switched on Nov 1 and can remain true indefinitely if forgotten. Add `request.time` cutoff condition with an explicit timezone decision (America/Chicago Nov 1 midnight = 2026-11-01T05:00:00Z due daylight time), plus optional early-shutdown flag; test dates/boundary. `registrationPath:'pin'` is client self-asserted and **does not verify a PIN**. It cannot grant access/accelerated approval; old PIN never authorizes protected data.
7. **Unprotected Admin data not yet migrated**: `/dangerZone`, `/moderation` etc. are not present in v2 and catchall denies them. This is fine until migration, but do NOT switch the website to Firestore reads until collections and scoped access are designed, tests pass and all data is migrated. `admin-data.enc.json` and old Git commit history remain historically decryptable to prior PIN holders; removal from current main doesn't erase old commits.
8. **29 tests are not included in pasted 'full rules' text**: The Slack file pasted only the rules plus notes; test descriptions/status may exist separately. Require a reproducible Emulator suite with reported results, plus denial/allow coverage for issues above, particularly status revoked with admin=true, guessed UID private read, malformed fields, squatted usernames, simultaneous registrations, Owner self-lockout attempts, server deadline cutoff. No tests completed by Cherish yet.
9. **Production deployment order**: Prefer review → emulator tests on exact rules → Owner email verification setup → user-authorized production rules release → authenticated integration tests with test identities → UI changes/data migration. Do not deploy untested changes first.
10. **Free plan**: Native Firebase email/password login; username is **display only**, so no Cloud Functions, username-to-email lookup or Blaze plan needed. Keep this owner-confirmed decision in the spec.
